# Database changes: school data management

Per-phase log for `school-data-management-plan.md`. Each entry: migration, reason, data impact, rollback, status. Nothing here has been applied to production. (The platform-wide log is `project plan/DATABASE-CHANGES.md`; D10 there is superseded by Phase 0 below.)

## Phase 0: D10, `Stream.academic_year` text to FK (branch `feat/school-data-management`, backend)

Reason: class year becomes a tenant-scoped reference (`academics.SchoolAcademicYear`) instead of free text.

| Migration | Type | Reversible | Notes |
|---|---|---|---|
| `academics.0009_stream_academic_year_fk` | AddField: nullable FK `academic_year_fk` to `SchoolAcademicYear`, `PROTECT` | yes | Generated by `makemigrations`. Additive; the text column is untouched. |
| `academics.0010_map_stream_academic_year` | Data (hand-written, like `accounts` 0013/0014) | yes | Maps `(school, trimmed, case-insensitive text)` to the year of the same school. Blank or whitespace becomes NULL. **If any non-blank value has no match it raises before writing anything and lists every unmatched `school / stream / value`.** Reverse copies the year name back into the text column. |
| `academics.0011_swap_stream_academic_year` | RemoveField (text `academic_year`) + RenameField (`academic_year_fk` to `academic_year`) | yes (restores an empty text column; 0010's reverse refills it) | Generated as two operations by `makemigrations`, merged into one file. Only reached after 0010 succeeds. |

Other changes in the same step:
- `check_stream_years` (read-only management command, raw SQL so it works before the migration). Lists unmatched streams, exits 1 if any. Run it first on every environment.
- API unchanged in shape: `academic_year` is still the year name (`""` when unset) on streams list/detail/summary/effective-subjects/bulk import. Writes accept a name, resolved inside the caller's school; an unknown name is a 400 (it was free text before). Streams `bulk_import` rows with an unknown year are now row errors.
- `seed_dev_users` creates the school's `2026` year and links the seed stream to it.

### Production order

1. Back up the database.
2. `manage.py check_stream_years` (read-only). Exit 0 means 0010 will map every stream; exit 1 lists the unmatched ones.
3. `manage.py ensure_school_years` (dry run, the default): prints the `SchoolAcademicYear` rows it would create, one per school and distinct non-blank stream text that has no match (trimmed, case-insensitive). Review the list: a typo such as `2O26` would become its own year, so fix the stream text first instead if that is what you see.
4. `manage.py ensure_school_years --apply` (add `--year 2026` to also give every school that year). Creates years only (one transaction); never edits streams or existing years and does not mark a year as current.
5. `manage.py check_stream_years` again: must print OK.
6. `manage.py migrate`. The new code expects the FK, so migrate before serving it; the old code breaks on the new schema.

Short form: `check_stream_years` -> `ensure_school_years --apply` -> `migrate`.

`ensure_school_years` is also read-before-write safe to re-run (idempotent). After the migration it only applies `--year`, because the text values no longer exist.

Data impact: none for matched or blank streams (values preserved as links/NULL). Streams with text that matches no year block the migration until fixed (by design).

Dev database (local SQLite, 2026-11-14): `check_stream_years` listed 2 unmatched (`Demo Seed A`, school 1, and `Rival Seed A`, school 2, both `'2026'`; the dev DB had no `SchoolAcademicYear` rows). `migrate` aborted at 0010 with those two listed and nothing changed. The two `2026` years were then created on the dev DB only and the migrations applied; 5 blank streams became NULL, 2 mapped. The same `migrate` also applied `accounts.0014_create_health_group`, which dev had not yet applied.

Production: not applied.

## Phase 1: foundations (branch `feat/school-data-management`, backend)

Reason: roles, an import report that can record skipped rows, `middle_name`, and clean NULLs for unique-nullable numbers, before the staff/parent/student phases need them. Not applied to production.

| Migration | Type | Reversible | Notes |
|---|---|---|---|
| `accounts.0015_create_principal_registrar_groups` | Data (`Group` rows `Principal`, `Registrar`, like 0013/0014) | yes (no-op: groups may hold members) | `get_or_create`, safe to re-run. Assign users to the groups in Django admin. |
| `accounts.0016_user_middle_name` | AddField `User.middle_name` (CharField 100, blank, default `''`) | yes | Generated by `makemigrations`. Existing users get `''`. Added to the user serializers (`UserSerializer`, `UserCreateSerializer`, directory) and to the existing student import (`middle_name` column). |
| `accounts.0017_blank_nemis_assessment_to_null` | Data | no-op reverse | `StudentProfile.nemis_number` / `assessment_number` are `unique=True, null=True` but forms/imports wrote `''`, so a second student without a NEMIS number collided. Existing `''` or whitespace-only values become NULL. Serializer and the student import now store NULL for blanks. Pre-check (read-only): `SELECT count(*) FROM accounts_studentprofile WHERE nemis_number = '' OR assessment_number = '';` (dev had 1 of each). |
| `academics.0012_bulkimportlog_skipped_count` | AddField `BulkImportLog.skipped_count` (PositiveInteger, default 0) | yes | Generated by `makemigrations`. Additive. |

Code changes with data/permission impact in the same step:
- `BulkImportLogViewSet` (import reports) is now restricted: ADMIN sees all types of their school; groups see only their types (Principal: streams, students, parents, staff; Registrar: students, parents; HR: staff). Teachers, other staff, parents and students get 403. Before, teachers could read it, including row errors that name admission/employee numbers.
- The streams import no longer swallows a failure to write its `BulkImportLog` row.
- New, unused until later phases: `core/imports.py` (limits 5 MB / 2000 rows, preview by default, rollback on unexpected errors, report + AuditLog on confirm, formula-safe templates/exports) and permission helpers `can_manage_staff_records`, `can_manage_learner_records`, `can_manage_classes` (+ classes `IsStaffRecordsManager`, `IsLearnerRecordsManager`, `IsClassManager`).

Deploy order: back up, `migrate` (0015 to 0017 and academics 0012 are independent of the Phase 0 migrations), then add users to the Principal/Registrar groups as needed.

Dev database (2026-11-14): backed up, then migrated; 0015 to 0017 and academics 0012 applied cleanly. The one blank `nemis_number`/`assessment_number` row became NULL; groups now Finance, HR, Health, Principal, Registrar. Production: not applied.
