# Database changes: school data management

Per-phase log for `school-data-management-plan.md`. Each entry: migration, reason, data impact, rollback, status. Nothing here has been applied to production. (The platform-wide log is `project plan/DATABASE-CHANGES.md`; D10 there is superseded by Phase 0 below.)

## Phase 0: D10, `Stream.academic_year` text to FK (branch `feat/school-data-management`, backend)

Reason: class year becomes a tenant-scoped reference (`academics.SchoolAcademicYear`) instead of free text.

| Migration | Type | Reversible | Notes |
|---|---|---|---|
| `academics.0009_stream_academic_year_fk` | AddField: nullable FK `academic_year_fk` to `SchoolAcademicYear`, `PROTECT` | yes | Generated by `makemigrations`. Additive; the text column is untouched. |
| `academics.0010_map_stream_academic_year` | Data (hand-written, like `accounts` 0013/0014) | yes | Maps `(school, trimmed, case-insensitive text)` to the year of the same school. Blank or whitespace becomes NULL. **If any non-blank value has no match it raises before writing anything and lists every unmatched `school / stream / value`.** Reverse copies the year name back into the text column. |
| `academics.0011_swap_stream_academic_year` | RemoveField (text `academic_year`) + RenameField (`academic_year_fk` to `academic_year`) | yes (restores an empty text column; 0010's reverse refills it) | Generated as two operations by `makemigrations`, merged into one file. Only reached after 0010 succeeds. |

Other changes in the same step:
- `check_stream_years` (read-only management command, raw SQL so it works before the migration). Lists unmatched streams, exits 1 if any. Run it first on every environment.
- API unchanged in shape: `academic_year` is still the year name (`""` when unset) on streams list/detail/summary/effective-subjects/bulk import. Writes accept a name, resolved inside the caller's school; an unknown name is a 400 (it was free text before). Streams `bulk_import` rows with an unknown year are now row errors.
- `seed_dev_users` creates the school's `2026` year and links the seed stream to it.

### Production order

1. Back up the database.
2. `manage.py check_stream_years` (read-only). Exit 0 means 0010 will map every stream; exit 1 lists the unmatched ones.
3. `manage.py ensure_school_years` (dry run, the default): prints the `SchoolAcademicYear` rows it would create, one per school and distinct non-blank stream text that has no match (trimmed, case-insensitive). Review the list: a typo such as `2O26` would become its own year, so fix the stream text first instead if that is what you see.
4. `manage.py ensure_school_years --apply` (add `--year 2026` to also give every school that year). Creates years only (one transaction); never edits streams or existing years and does not mark a year as current.
5. `manage.py check_stream_years` again: must print OK.
6. `manage.py migrate`. The new code expects the FK, so migrate before serving it; the old code breaks on the new schema.

Short form: `check_stream_years` -> `ensure_school_years --apply` -> `migrate`.

`ensure_school_years` is also read-before-write safe to re-run (idempotent). After the migration it only applies `--year`, because the text values no longer exist.

Data impact: none for matched or blank streams (values preserved as links/NULL). Streams with text that matches no year block the migration until fixed (by design).

Dev database (local SQLite, 2026-11-14): `check_stream_years` listed 2 unmatched (`Demo Seed A`, school 1, and `Rival Seed A`, school 2, both `'2026'`; the dev DB had no `SchoolAcademicYear` rows). `migrate` aborted at 0010 with those two listed and nothing changed. The two `2026` years were then created on the dev DB only and the migrations applied; 5 blank streams became NULL, 2 mapped. The same `migrate` also applied `accounts.0014_create_health_group`, which dev had not yet applied.

Production: not applied.

Code changes with data/permission impact in the same step:
- `BulkImportLogViewSet` (import reports) is now restricted: ADMIN sees all types of their school; groups see only their types (Principal: streams, students, parents, staff; Registrar: students, parents; HR: staff). Teachers, other staff, parents and students get 403. Before, teachers could read it, including row errors that name admission/employee numbers.
- The streams import no longer swallows a failure to write its `BulkImportLog` row.
- New, unused until later phases: `core/imports.py` (limits 5 MB / 2000 rows, preview by default, rollback on unexpected errors, report + AuditLog on confirm, formula-safe templates/exports) and permission helpers `can_manage_staff_records`, `can_manage_learner_records`, `can_manage_classes` (+ classes `IsStaffRecordsManager`, `IsLearnerRecordsManager`, `IsClassManager`).

Deploy order: back up, `migrate` (0015 to 0017 and academics 0012 are independent of the Phase 0 migrations), then add users to the Principal/Registrar groups as needed.

Dev database (2026-11-14): backed up, then migrated; 0015 to 0017 and academics 0012 applied cleanly. The one blank `nemis_number`/`assessment_number` row became NULL; groups now Finance, HR, Health, Principal, Registrar. Production: not applied.

## Pre-flight for Phase 2/3/4 migrations: `check_duplicates` (read-only)

`manage.py check_duplicates` lists, per school (values trimmed, case-insensitive): duplicate student `admission_number`, staff `employee_number`, staff `national_id_no`, and parent `national_id_no` (reported as "skipped" until `accounts_parentprofile` exists, i.e. before Phase 3). It writes nothing, uses raw SQL (works before the migrations it guards), and exits 1 if any duplicate exists.

**It must print `OK: no duplicates.` (exit 0) on production before running the Phase 2 migrations (`accounts.0018`-`0020`), and again before the Phase 3 and Phase 4 migrations that add unique constraints.** Its output contains national IDs: run it on the server and do not paste it into tickets. Dev (2026-11-15, before Phase 2 migrate): all four checks OK / parent check skipped.

## Phase 2: staff (branch `feat/school-data-management`, backend)

Reason: configurable staff groups, a DB guarantee that a national ID is unique within a school, server-side import. Not applied to production.

| Migration | Type | Reversible | Notes |
|---|---|---|---|
| `accounts.0018_staffgroup_and_free_group` | CreateModel `StaffGroup` (school, name, is_default; unique on `(school, lower(name))`) + AlterField `StaffProfile.group` (drops `choices`, same column and values) | yes | Generated by `makemigrations`. `group` stays a text column; it is validated against the school's `StaffGroup` rows in the API instead of a fixed list. |
| `accounts.0019_staff_groups_and_national_ids` | Data (hand-written, like 0013/0014/0017) | no-op reverse | (1) Trims staff national IDs and stores blank/whitespace as NULL. (2) **Aborts before writing anything if two staff of one school share a national ID**, listing school, ID, name and employee number of each. (3) Creates the five default groups for every school (marked default) plus any other `group` text already in use (not default). Safe to re-run. |
| `accounts.0020_unique_staff_national_id` | AddConstraint (unique `(school, national_id_no)` where not NULL and not blank) | yes | Generated by `makemigrations`. Reached only after 0019 succeeds. |

Order on production: back up, `check_duplicates` (must be OK), `migrate`. If 0019 aborts, fix the listed records (clear or correct one of each pair) and migrate again; nothing was changed.

Code changes with data/permission impact:
- `StaffProfileViewSet`: ADMIN and the HR group see and edit all staff of their school, including national ID. Before, HR users saw only their own row (HR visibility bug). The Principal group reads all staff through a slim serializer (no national ID) and cannot write. Teachers and other STAFF see only their own row, slim. Parents/students 403.
- Search by national ID works for ADMIN/HR only.
- Deactivating, or deleting, a staff member who supervises an active class (via the linked user's `ClassTeacher` rows) is refused (400) with the class names.
- New `staff-groups` API: all staff-record readers list; ADMIN/HR add; default groups cannot be renamed or deleted; a group with staff cannot be deleted; renaming a custom group moves its staff.
- `staff-profiles/template/` (7 columns exactly: NAME, PHONE, TITLE, GENDER, NATIONAL_ID_NO, EMPLOYEE NUMBER, GROUP; `?fmt=xlsx`) and `staff-profiles/bulk_import/` now on `core/imports.py`: multipart CSV/XLSX (or the old JSON `staff` list), preview by default, `confirm=true` re-parses and re-validates the uploaded file, ADMIN/HR only. Linking by email happens only to an existing TEACHER/STAFF account of the same school without a staff record; no account is ever created.
- Staff records are now in the audit log (create/update/delete); snapshots hold employee number, group, status and user id, never the national ID.
- `core/imports.py`: `escape_cell` unchanged (strings only); parsing now removes exactly one apostrophe that protects a formula-looking value (`'+254712345678` becomes `+254712345678`), so export then import round-trips.

## Phase 3: parents (branch `feat/school-data-management`, backend)

Reason: one real parent with several children, contact details in one place, fixed relationship values. Not applied to production.

| Migration | Type | Reversible | Notes |
|---|---|---|---|
| `accounts.0021_parent_profile_and_relationship` | CreateModel `ParentProfile` (user 1:1, school, national_id_no, alt_phone, address, occupation, gender; unique `(school, national_id_no)` where not NULL and not blank) + AlterField `ParentLearner.relationship` (choices FATHER/MOTHER/GUARDIAN/OTHER, default GUARDIAN; same column) | yes | Generated by `makemigrations`. The table is new and empty, so the constraint cannot fail. |
| `accounts.0022_map_parent_relationships` | Data (hand-written) | no-op reverse | Maps existing free text (case/space-insensitive): father/dad to FATHER, mother/mum/mom to MOTHER, guardian to GUARDIAN, everything else (including the old default `Parent`, and blank) to OTHER. Creates an empty `ParentProfile` for every PARENT user that has a school. Safe to re-run. |

Order on production: back up, `check_duplicates` (parent check is skipped until 0021 exists; nothing to dedupe yet), `migrate`. National IDs for existing parents are blank, so no clash is possible until they are filled in; the constraint then rejects a second parent with the same ID in one school.

Code changes with data/permission impact:
- New `parents/` API (`/api/auth/parents/`, id = the parent's user id). ADMIN and Registrar: full record (national ID, alternate phone, address) and write. Principal: read-only, slim (no national ID, address, alternate phone; national ID not searchable). Teachers, other staff, parents, students: 403. Delete refused while the parent has linked learners.
- `users/parents/` and `users/?role=PARENT`: a parent's `phone` is removed for everyone except ADMIN, Registrar, Principal and the parent themself (teachers no longer see parent phones). The Registrar and Principal can now open the `users/parents/` directory.
- `parent-learner-links`: read for any signed-in user (parent sees only their own links, as before); write for ADMIN, Registrar, Principal. Registrar/Principal list all links of their school. `relationship` must be one of the four codes (400 otherwise).
- `accounts/parents.py`: `match_or_create_parent(school, national_id, phone, email)`: national ID, then phone (normalised to 254...), then email, always inside the school. A phone/email match whose national ID differs raises `ParentConflict` (never merged). Fills blank profile fields only. New parents get an unusable password; nothing is emailed.
- Old `users/bulk_import` now stores a valid relationship code (`Parent` becomes GUARDIAN); the rest of it is replaced in Phase 4.
